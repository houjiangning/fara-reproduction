FaR 比特流「假新版」问题定位与修复

L2 报 VERSION=0x0001_0000 / FaRMap=0xDEADBEEF —— 根因在 Vivado 的 module-reference OOC 综合，不在板卡。

ZCU106 · up_proj GEMM · Vivado 2022.2 · 2026-10-05

1现象

板卡侧 gemm_probe 与 run_far.sh 的 L2 结果：

VERSION  (0x18) = 0x00010000   expect 0x00020000   FAIL
M_ROWS   (0x08) = 0x00000010   expect 0x00000010   OK
N_TILES  (0x1C) = 0x000000C0   expect 0x000000C0   OK
K_COLS/N_TOKENS/LAYER_ID  读写回环                          OK
FAR_NENT (0x34) = 0xDEADBEEF   expect 0x00000008   FAIL
FAR_A[0] (0x3C) = 0xDEADBEEF   expect 0x000002FF   FAIL
FAR_INV  (0x40) = 0xDEADBEEF   expect 0x3F000000   FAIL

关键判读：AXI-Lite 通路完全正常（常量寄存器读得对、读写回环都对），只是这一份 PL 里装的是一颗 能跑、但没有 FaR 的旧 GEMM。所以这不是连线 / 地址 / 时钟问题，而是比特流内容本身是旧的。

2根因

GEMM 在 Block Design 里是以 module reference 的形式挂进去的：

up_proj.bd :
  "gemm_up_proj_bd_0": {
    "vlnv"      : "xilinx.com:module_ref:gemm_up_proj_bd:1.0",
    "xci_name"  : "up_proj_gemm_up_proj_bd_0_0",
    "inst_hier_path": "gemm_up_proj_bd_0" }

Vivado 对 module reference 做 OOC（out-of-context）综合，产物是一份独立的 checkpoint：

up_proj_gemm.gen\sources_1\bd\up_proj\ip\up_proj_gemm_up_proj_bd_0_0\
        up_proj_gemm_up_proj_bd_0_0.dcp     <-- 就是这一份被链接进了最终比特流
这份 DCP 的时间戳是 2026-10-01 20:02，比 FaR RTL 还老
rtl/far_reroute.sv          2026-10-05 09:03
rtl/gemm_up_proj_core.sv   2026-10-05 09:04
rtl/gemm_up_proj_axi_lite.sv 2026-10-05 09:12
rtl/gemm_up_proj_top.sv    2026-10-05 09:13
up_proj_gemm_up_proj_bd_0_0.dcp  2026-10-01 20:02  <-- 旧

2026-10-05 的重建过程只刷新了这个 IP 的 .xci / .xml（11:08:43）， 却没有重跑 OOC 综合。于是：

  1. synth_1（11:11）把 up_proj_gemm_up_proj_bd_0_0 当成 BlackBox 处理 —— 顶层综合日志的 Report BlackBoxes 明确列了它。
  2. impl_1 的 link_design（11:14）去读那个 10-01 的旧 DCP 来填充这个黑盒 —— 日志原文：Reading design checkpoint '...up_proj_gemm_up_proj_bd_0_0.dcp' for cell 'up_proj_i/gemm_up_proj_bd_0'。
  3. 11:22 写出的 up_proj_wrapper.bit.bin 里装的就是没有 FaR 的旧 GEMM： VERSION 常量 0x0001_0000，0x30~0x54 未译码（读回 0xDEADBEEF）。

为什么旧的重建脚本没能拦住

rebuild_bitstream.tcl 原来靠这段来"作废 BD 的 OOC run"：

foreach r [get_runs -quiet -filter {IS_SYNTHESIS}] {
  if {[string match "*bd_0_0_synth_1" $r]} { reset_run $r }
}

但 up_proj_gemm_up_proj_bd_0_0_synth_1 根本不是工程里的 run （它是 BD 的 output product），get_runs 里查不到它 —— 这个循环一个都没匹配上， 于是旧 DCP 被原样复用，全程无任何报错。

教训：SHA256 一致 ≠ 内容正确

之前"本地 .bit.bin 与板卡文件 SHA256 相同"只能证明文件传输成功， 不能证明这份文件里有 FaR。两者当时都指向同一份旧的、错误的比特流。

3修复（一条命令）

tools/rebuild_bitstream.tcl 已修好，现在会：

  • 先把 BD 的 output products reset_target + generate_target， 强制 module reference 重新 OOC 综合；若 Vivado 不接受 reset_target，则删掉旧 DCP 再生成。
  • 加了一道硬门禁：新 DCP 的时间戳必须 晚于最新 RTL；否则直接 error 退出， 绝不静默产出旧比特流。

前置：Vivado 工程必须在 GUI 里关掉（batch 会独占工程）。

cd C:\Users\houji\Desktop\doc\study\llm-fpga-security-literature\fara-reproduction\fpga\up_proj_gemm
powershell -ExecutionPolicy Bypass -File tools\rebuild_bitstream.ps1

日志看 up_proj_gemm\rebuild_bitstream.log。关心这几行：

== OOC dcp (before): 2026-10-01 20:02:36

7期望寄存器值（L2 判据）

偏移寄存器期望含义
0x08M_ROWS0x00000010M_TILE = 16
0x0CK_COLSrw规约深度，可写回读
0x10N_TOKENSrwtoken 数
0x14LAYER_IDrw层标识
0x18VERSION0x00020000FaR 版判据（0x00010000 = 旧纯 GEMM）
0x1CN_TILES0x000000C0M_TOTAL/M_TILE = 192
0x34FAR_NENT0x00000008FaRMap 条目数
0x3CFAR_A[0]0x000002FF条目 0 的地址
0x40FAR_INV[0]0x3F000000条目 0 的供体列
0x60 / 0x80未译码地址0xDEADBEEF故意保留的"空地址"哨兵值
如果新比特流烧上去后 VERSION 仍是 0x00010000

那就说明问题从"比特流是旧的"转移到了"新比特流没真正加载"。此时检查： 板上文件大小是否已变、firmware_class 的 path 指向是否正确、 dmesg 里 fpga_manager 是否有报错、以及 PL 是否被上一次的配置占着没刷新。
